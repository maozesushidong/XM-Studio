# 需求分析输出与需求档案字段

使用能保留共识的最小结构。对话中只输出当前进展；只有钉钉业务需求机器人渠道在业务明确确认最终摘要后自动创建正式需求档案。用户与 Codex、Hermes、Claude 直接沟通默认不创建REQ，除非本轮明确要求“纳入需求池/生成REQ/走数智审核”。

## 渠道门禁（CHANNEL_GATE_DIRECT_AGENT_NO_AUTO_REQ）

- 钉钉业务需求机器人 + 业务确认：自动建REQ，状态为“待数智审核”，并通知梦蝶。
- 直接 Agent 会话：可以输出分析、PRD或项目写回，但默认不建REQ、不进入数智审核、不通知。
- 直接 Agent 会话只有本轮明确要求入池时才使用以下正式档案结构。
- 渠道不明时默认不存档、不通知。

## 对话进展

每两到三轮有效对话输出一次：

1. **当前理解**：一小段业务语言。
2. **已确认事实**：只写业务明确确认的新增事实。
3. **假设 / 待确认 / 分歧 / 需求分支**：分开列示，不能混写。
4. **下一个问题**：一个高价值主问题，最多附带一个不可分割的关联问题。

业务明确确认前，状态只能是“理解进行中”或“待业务确认”。不要每轮发布完整分析。

### 面向业务的收尾话术

- 已完成业务确认、尚未通过数智部门审核立项：`目前已完成业务需求收集与确认，尚未正式立项，后续将提交数智部门评估审核。审核通过后，再进入产品方案及后续实施阶段。`
- 仅完成初步收集、尚未业务确认：`目前已完成初步需求收集，相关内容仍待业务确认；确认后将提交数智部门评估。`
- 不主动对业务说“尚未保存正式需求档案”“未进入PRD、原型或开发阶段”。这些属于内部流转信息，仅在对方明确询问时解释。

## 正式需求档案路径

`{KNOWLEDGE_BASE}/10_先马电商/02_需求与规划/01_需求池/需求档案/YYYY/REQ-YYYYMMDD-序号_需求名称.md`

- Markdown 是需求事实源。
- 状态保留在同一文件中更新，不因状态变化移动文件。
- 允许状态：理解进行中、待业务确认、待数智审核、已确认、已进入项目、已进入PRD、已进入开发、已完成、暂缓、已拒绝。
- 仅当钉钉业务渠道通过门禁，或直接 Agent 会话本轮明确要求入池时，才允许存档；初始正式状态为“待数智审核”，数智审核通过后才改为“已确认”。
- 仅对通过渠道门禁创建的REQ执行 `{NOTIFY_SERVICE} "<REQ绝对路径>"` 私信梦蝶。通知失败只进入持久重试队列，不回滚REQ。
- 关联项目未知时写“待归属确认”。
- 完整流转规则：`{KNOWLEDGE_BASE}/10_先马电商/02_需求与规划/01_需求池/需求流转与项目关联规则.md`。

## YAML 元数据

```yaml
---
requirement_id: REQ-YYYYMMDD-序号
title: 需求名称
status: 待数智审核
requester: 待确认
source: 钉钉机器人 / 用户提供的材料 / 其他
source_channel: dingtalk_business_bot / direct_agent_explicit_opt_in
submitted_date: YYYY-MM-DD
related_departments: []
related_projects: []
project_input_links: []
product_output_links: []
knowledge_sources: []
confirmation_status: 已确认
last_updated: YYYY-MM-DD
---
```

日期、人员、部门、数字和成功标准只能来自用户或可验证事实；未知则写“待确认”，不得猜测。

## 正文必备字段

### 1. 基本信息
- 需求编号
- 标题
- 状态
- 提出人 / 来源
- 提出日期
- 关联部门
- 关联项目

### 2. 原始诉求与背景
- 原始诉求摘要
- 为什么现在提出
- 最近一次真实案例

### 3. 当前流程与真实问题
- 当前流程
- 当前替代方式
- 真实问题和瓶颈
- 角色 / 场景
- 影响 / 频率 / 证据

### 4. 期望与边界
- 期望结果
- 可观察的成功标准
- 范围
- 非范围
- 约束 / 风险
- 异常分支

### 5. 信息状态
- 已确认事实
- 假设
- 待确认项（区分强阻断和可后置）
- 分歧
- 独立需求分支

### 6. 确认、证据、检索与项目路由
- 业务确认记录：确认人、确认时间、确认原文或可核验依据
- 需求证据：正式SOP、需求专属证据目录、其他证据链接
- 知识库检索记录：识别项目与模块、实际读取的事实源、现状状态、冲突或资料缺口、本轮确认覆盖内容
- 关联项目和项目业务输入入口
- 产品输出：PRD、方案、原型及其反向链接
- 下一阶段授权状态
- 开发、验收和复盘证据

知识库检索记录只填写实际读取过的资料，必须区分已上线、已确认规则、当前原型、待开发、历史版本和待确认。

## 证据规则

- 不自动抓取或保存完整钉钉聊天历史。
- 只使用用户明确提供的聊天导出、录音、转写、截图和附件作为证据。
- 临时附件先按SHA-256查重；知识库已有相同文件时只链接，不重复复制。
- 可跨需求复用的正式SOP、制度和项目资料进入对应业务目录；需求专属证据进入 `需求证据/YYYY/REQ-.../`。
- 正式归档、哈希校验和链接验证完成后才能清理临时副本。
- 过滤寒暄、重复试错和无价值噪声；只沉淀影响问题、范围、决策或证据的信息。
- 不保存密钥、隐私或无长期留存必要的敏感信息；必要内容先脱敏，或仅保存受控链接。

## 链接与交接

- REQ需求档案是唯一正文事实源。
- 项目现有 `01_业务输入`、`01业务输入` 或 `业务输入` 中的 `需求入口.md` 只建立REQ、SOP和证据链接。
- PRD、方案和原型进入项目现有产品输出目录，并直接链接REQ和项目需求入口。
- 创建产品输出后，必须回写REQ“产品输出”和项目 `需求入口.md`，完成双向链接。
- 需求分析确认不代表 PRD、原型或开发授权。
- 只有用户明确要求写 PRD 时才路由：先马 AI 设计平台使用 `xianma-ai-design-platform-prd`；没有专用能力且明确要求通用 PRD 时使用 `prd-writer`。
