# 项目识别与知识库按需检索

## 触发时机

处理每一条新业务诉求时都维护候选项目：

- 原始输入已经明确项目或模块：在提出第一个实质性问题前检索；
- 首轮无法判断：先按首轮硬约束问一个真实场景问题；一旦项目或模块变得明确，在下一次追问前检索；
- 项目始终不明确：保持待归属确认，不扫描全部项目。

## 必须读取的路由表

`{KNOWLEDGE_BASE}/10_先马电商/02_需求与规划/01_需求池/需求项目路由与知识库映射.md`

路由表是项目定位事实源。关键词只能提供候选，不得替代业务语义判断。

## 检索步骤

1. 从用户输入提取业务对象、动作、系统、角色和模块词。
2. 对照路由表确定高、中或低置信度候选项目。
3. 高置信度：读取项目一级入口；中置信度：先读主要候选入口，仍歧义时只问一个项目归属问题；低置信度：不批量读取项目。
4. 在一级入口中定位具体模块，只读取与本轮问题直接相关的模块节点、正式规则和当前产物。
5. 记录实际读取的文件、文件日期、状态和冲突；不得填写未实际读取的来源。
6. 执行已有能力对比，将诉求归为：可直接使用已有能力、已有部分能力需要增强、当前无对应能力。
7. 根据“已知现状与用户诉求的差距”生成下一个问题，而不是从通用问卷取题。

首次项目检索优先控制在3到5个文件。只有发现跨模块影响、事实冲突或版本不明时才扩展检索。

## 事实优先级与状态

按以下顺序处理冲突：

1. 用户本轮明确确认；
2. 已确认模块规则或正式决策；
3. 项目记忆中的较新确认记录；
4. 当前功能清单和当前可观察原型；
5. 旧PRD、会议、历史版本和工作过程资料。

必须标记：

- 已确认规则
- 已上线
- 当前原型
- 当前原型占位
- 待开发 / 规划目标
- 历史版本
- 待确认

资料中的整理日期较早时，不得覆盖之后的确认记录。文件名带“当前”也不能替代日期和内容核对。

## 对话输出约束

知识库检索用于减少问题，不用于展示检索量。

推荐结构：

`一句与当前诉求直接相关的现状或差距 + 一个问题`

例如：

`当前AI买家秀已有单商品的场景化生成和任务结果链路。你说的批量是多个商品一起处理，还是同一商品一次生成多套风格？`

当业务提出“新增功能”但平台已有相近能力时，必须先告知已有能力，再确认差异。示例：

`目前平台已有 AI商品套图、AI买家秀、批量美颜等批量能力。你这次是想批量生成新图片，还是批量修改已有图片？`

禁止：

- 输出长篇项目资料摘要；
- 罗列所有现有功能；
- 把知识库内容当成业务人员本轮已经确认；
- 重复询问知识库已经明确且没有冲突的事实；
- 因检索到PRD或原型而切换到PRD或实现阶段。
- 未完成已有能力对比，就把“新增/增加”直接视为平台没有该能力。

## 检索失败与冲突

- 路径不存在：尝试项目一级入口中的现行链接；仍不存在则标记资料路径失效，不猜新路径。
- 多个版本均声称当前：读取项目记忆和版本说明；仍无法判断时只问一次目标版本。
- 知识库与业务表述冲突：简短说明冲突，只问决定本次需求口径的一个问题。
- 外部线上系统需要登录、积分或危险操作：没有明确授权时仅使用本地事实源，不自动操作线上系统。

## 正式需求档案

保存REQ时，在 YAML 添加：

```yaml
knowledge_sources: []
```

正文增加“知识库检索记录”，包括：

- 识别项目与模块；
- 实际读取的事实源；
- 检索到的现状及其状态；
- 冲突或资料缺口；
- 本轮业务确认覆盖的内容。

只记录实际读取过的资料。知识库检索记录是来源追溯，不是第二份项目总结。
