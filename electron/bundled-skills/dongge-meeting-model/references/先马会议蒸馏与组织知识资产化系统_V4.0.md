# 先马会议蒸馏与组织知识资产化系统 V4.0

> **一句话定位：**
> 把一次会议中的原始交流，蒸馏成可追溯的事实、清晰的判断、明确的决策、可复用的方法、可执行的任务、可验收的结果，以及可供人、AI和数字员工持续调用的组织知识资产。

---

# 〇、文件用途

本文件既是公司高管层使用的会议管理标准，也是可以直接交给各自 AI 执行的结构化规范。

它同时解决四个问题：

1. **会议结束后，大家是否真正理解了同一件事；**
2. **会议是否形成了明确决策、任务和责任闭环；**
3. **会议中的经验和判断是否沉淀成可复用的方法；**
4. **这些方法是否可以进一步进入知识库、RAG、Prompt、SOP、Spec和数字员工。**

本系统不以“记录得多不多”为标准，而以以下结果为标准：

> 下一次遇到同类问题时，组织能否比上一次判断得更快、行动得更准、返工得更少、结果更稳定。

---

# 一、为什么要从“会议纪要”升级为“会议蒸馏”

传统会议纪要主要解决：

- 谁说了什么；
- 会议形成了哪些结论；
- 接下来要做哪些事情。

会议蒸馏进一步解决：

- 会议真正要解决的底层矛盾是什么；
- 为什么做出这样的判断和取舍；
- 哪些已经决策，哪些仍然未决；
- 哪些经验可以沉淀为方法、规则和标准；
- 哪些内容可以转成SOP、Prompt、Spec、RAG和Agent；
- 如何在下次复盘中验证本次判断是否正确。

| 对比维度 | 传统会议纪要 | 会议蒸馏 V4.0 |
|---|---|---|
| 核心目标 | 记录会议内容 | 生产决策、行动与知识资产 |
| 关注重点 | 发言和结论 | 矛盾、判断、决策、方法、任务、验收 |
| 服务对象 | 参会人员 | 管理者、执行者、新员工、AI、数字员工 |
| 时间价值 | 服务本次会议 | 服务未来同类业务场景 |
| 主要交付 | 一份纪要 | 主文档、任务台账、决策地图、方法卡、AI资产 |
| 判断标准 | 是否记录完整 | 是否能推动结果并形成组织复利 |

## 1. 会议信息：还原会议场景与权责关系

### 1.1 核心目的

回答：

> 这是一场什么会议，为什么现在开，谁拥有决策权，谁承担最终结果？

### 1.2 必须提取的字段

| 字段 | 说明 |
|---|---|
| 会议名称 | 使用能反映真实议题的名称 |
| 会议日期 | 明确到年月日 |
| 开始与结束时间 | 能确定时填写，不能确定则标注 |
| 会议时长 | 根据录音或记录计算 |
| 会议形式 | 线下、线上、混合、电话、访谈 |
| 会议类型 | 战略会、经营会、复盘会、项目会、需求会、培训会、蒸馏会等 |
| 显性主题 | 会议表面上讨论什么 |
| 真实议题 | 会议真正要推动什么变化 |
| 触发背景 | 为什么必须在当前节点开会 |
| 发起人 | 谁推动会议发生 |
| 决策人 | 谁拥有最终拍板权 |
| DRI | 谁对最终结果负责 |
| 业务专家 | 谁掌握关键专业知识 |
| 执行负责人 | 谁负责后续动作 |
| 验收人 | 谁确认交付结果 |
| 关键参与人 | 其他影响决策或执行的人 |
| 受影响对象 | 哪些部门、岗位、客户或系统受到影响 |
| 资料来源 | 录音、视频、转写、PPT、表格、群聊等 |
| 信息质量 | 是否存在转写错误、缺失、人名不清、术语误识别 |

### 1.3 角色识别标准

| 角色 | 英文缩写 | 责任 |
|---|---|---|
| 发起人 | Sponsor | 发起并推动事项 |
| 决策人 | Decision Maker | 拥有最终拍板权 |
| 最终负责人 | DRI | 对结果承担唯一责任 |
| 领域专家 | Domain Expert | 提供专业判断与标准 |
| 执行者 | Executor | 完成具体任务 |
| 验收人 | Reviewer | 判断交付是否合格 |
| 利益相关人 | Stakeholder | 会受到结果影响 |
| 质疑者 | Challenger | 提供反证、质疑和不同视角 |

### 1.4 验收标准

读者在30秒内能够判断：

- 这场会为什么重要；
- 谁能拍板；
- 谁对结果负责；
- 谁负责执行；
- 会议所处的业务背景是什么。

## 2. 一句话判断：提炼会议的核心矛盾

### 2.1 核心目的

不是复述会议主题，而是回答：

> 这场会议表面上在讨论什么，实质上到底在解决什么矛盾？

### 2.2 标准结构

一句话判断应尽量包含：

1. 表层议题；
2. 底层矛盾；
3. 核心取舍；
4. 解决方向；
5. 未决条件。

### 2.3 通用模板

> 这场会表面上在讨论【表层问题】，实质上是在解决【底层矛盾】；核心取舍是从【旧状态】转向【新状态】，会议初步决定通过【关键路径】解决，但仍受制于【风险、依赖或未决条件】。

### 2.4 禁止写法

以下表达不构成有效判断：

- 本次会议讨论了AI应用；
- 本次会议沟通了项目进度；
- 大家就业务问题进行了深入交流；
- 本次会议对下一阶段工作作出安排。

这些只是主题复述，没有揭示真正矛盾。

### 2.5 验收标准

一句话判断必须回答：

- 原来的方式为什么不行；
- 真正的主要矛盾是什么；
- 准备转向什么新状态；
- 会议确定的突破口是什么；
- 还有什么没有解决。

## 3. 会议精神：明确组织的状态转移

### 3.1 核心目的

回答：

> 本次会议要求组织、业务或个人，从什么旧状态转向什么新状态？

### 3.2 核心表达方式

必须优先采用：

> **从A转向B。**

例如：

| 旧状态 | 新状态 |
|---|---|
| 从依赖个人经验和口头传递 | 转向方法、标准和系统化沉淀 |
| 从只讨论问题 | 转向形成决策、任务和验收 |
| 从旧流程上增加AI工具 | 转向围绕目标重构AI原生流程 |
| 从多人参与但无人负责 | 转向每项任务设唯一DRI |
| 从完成文档 | 转向产生真实业务结果 |
| 从一次性会议 | 转向会议—执行—复盘—再蒸馏闭环 |

### 3.3 建议输出四类内容

| 类型 | 要回答的问题 |
|---|---|
| 开始做什么 | 会议要求新增哪些动作 |
| 停止做什么 | 哪些旧习惯和旧做法不再接受 |
| 坚持什么 | 哪些原则不能因短期困难而改变 |
| 不能误解成什么 | 防止会议精神被表面化和形式化 |

### 3.4 禁止写法

不得用以下空泛表达代替状态转移：

- 高度重视；
- 加强协同；
- 持续推进；
- 统一思想；
- 提升认识；
- 全力以赴。

### 3.5 验收标准

读完后，管理者和执行者都能明确：

- 今后要采用什么新方式；
- 哪些旧状态不再被允许；
- 哪些行为将成为新的管理标准。

## 4. 方法论：把会议经验晶化成可复用方法

### 4.1 核心目的

回答：

> 本次会议中，有哪些知识不仅适用于当前问题，还能用于下一次同类场景？

### 4.2 方法卡标准字段

| 字段 | 说明 |
|---|---|
| 方法名称 | 可传播、可检索、可调用的名称 |
| 一句话定义 | 用一句话说明方法本质 |
| 解决问题 | 解决什么具体卡点 |
| 适用场景 | 什么情况下使用 |
| 不适用场景 | 什么情况下不得使用 |
| 前置条件 | 使用前必须具备什么 |
| 输入物 | 需要哪些资料、数据、权限 |
| 核心动作 | 分步骤说明怎么做 |
| 输出物 | 最终交付什么 |
| 判断标准 | 怎么判断方法是否有效 |
| 常见错误 | 最容易在哪些地方跑偏 |
| 正例 | 正确应用案例 |
| 反例 | 错误应用案例 |
| 原文锚点 | 方法来自会议哪一段 |
| AI化方式 | 是否可转SOP、Prompt、Spec、Agent |
| 复审周期 | 什么时候重新验证 |

### 4.3 方法论四级形态

| 层级 | 说明 |
|---|---|
| 观点 | 对事情的看法 |
| 方法 | 说明怎么做 |
| 规则 | 说明什么情况下怎么判断 |
| 系统 | 能被持续执行、验收、反馈和迭代 |

### 4.4 验收标准

一项内容只有同时具备以下要素，才能进入正式方法库：

- 有明确场景；
- 有具体步骤；
- 有适用边界；
- 有交付物；
- 有判断标准；
- 有正反案例；
- 有原文证据；
- 有复审机制。

## 5. 思路链：还原从问题到结果的推演过程

### 5.1 核心目的

回答：

> 会议如何从发现问题，走到判断、结构、动作、验收和复盘？

### 5.2 标准模型：P-J-S-A-V-R

| 环节 | 英文 | 要回答的问题 |
|---|---|---|
| 问题 | Problem | 表层问题和根因问题分别是什么 |
| 判断 | Judgment | 对问题作出什么判断，依据是什么 |
| 结构 | Structure | 问题由哪些模块、变量、角色和流程组成 |
| 动作 | Action | 先做什么，后做什么，谁来做 |
| 验收 | Verification | 做到什么程度算完成 |
| 复盘 | Review | 什么时候检查，错误时怎么调整 |

### 5.3 标准写法

> 当前表层问题是【A】，但根因是【B】；会议判断【C】才是主要矛盾，依据是【D】。结构上拆成【模块1、模块2、模块3】，动作上先做【第一步】，再做【第二步】，最终通过【交付物、数据或样例】验收，并于【日期】复盘。

### 5.4 验收标准

完整思路链必须能回答：

- 为什么这样判断；
- 为什么先做这个；
- 为什么不做另一个；
- 谁来执行；
- 做成什么样；
- 错了如何修正。

---

## 6. 任务安排：形成责任、时间、交付与验收闭环

### 6.1 核心目的

回答：

> 谁，在什么时间前，交付什么，由谁按照什么标准验收？

### 6.2 标准任务字段

| 字段 | 说明 |
|---|---|
| 任务编号 | 用于持续跟踪 |
| 任务名称 | 必须以动词开头 |
| 任务背景 | 为什么要做 |
| DRI | 唯一最终负责人 |
| 协同人 | 谁提供配合 |
| 开始时间 | 何时启动 |
| 截止时间 | 何时交付 |
| 阶段里程碑 | 中间检查节点 |
| 输入资料 | 所需数据、文档、权限 |
| 交付物 | 最终提交什么 |
| 验收标准 | 做到什么程度算完成 |
| 验收人 | 谁确认结果 |
| 原文锚点 | 任务源自会议哪一段 |
| 依赖条件 | 依赖哪些人、系统或数据 |
| 风险备注 | 哪些因素可能造成延期或返工 |
| 当前状态 | 未开始、进行中、阻塞、完成、关闭 |

### 6.3 命名规范

错误：

> AI流程优化。

正确：

> 完成视觉中心商品主图生产流程的现状图、AI化新流程图、岗位SOP和10条验收样例。

### 6.4 验收规范

错误：

> 完成方案。

正确：

> 交付业务流程图、岗位分工表、输入输出字段表和10条真实验收样例，并由业务负责人和技术负责人共同验收。

### 6.5 验收标准

任何任务缺少以下任一项，都不得进入正式行动台账：

- 唯一DRI；
- 截止时间；
- 明确交付物；
- 验收标准；
- 验收人；
- 原文锚点。

## 7. 风险与回退：建立会议决策的失控预警机制

### 7.1 核心目的

回答：

> 这项决策或任务，最可能在哪里返工、跑偏、延期、失控或造成错误？

### 7.2 标准风险字段

| 字段 | 说明 |
|---|---|
| 风险名称 | 风险是什么 |
| 风险类型 | 战略、业务、组织、技术、数据、成本、合规等 |
| 触发条件 | 什么情况下发生 |
| 预警信号 | 发生前会出现什么迹象 |
| 影响范围 | 会影响什么 |
| 发生概率 | 高、中、低 |
| 影响程度 | 高、中、低 |
| 风险负责人 | 谁持续观察 |
| 预防措施 | 如何降低发生概率 |
| 回退方案 | 发生后退回到哪个安全状态 |
| 升级条件 | 什么情况下必须上报 |
| 原文锚点 | 风险来自哪段讨论 |

### 7.3 常见风险类型

- 理解跑偏；
- 目标虚化；
- 任务没有交付物；
- 责任人不唯一；
- 验收标准缺失；
- 数据口径冲突；
- AI幻觉；
- 过度工程化；
- 旧流程惯性；
- 跨部门协同失效；
- 成本和资源超预算；
- 权限和合规问题；
- 方法被错误迁移；
- 知识过期；
- 没有安全回退。

### 7.4 验收标准

每一项高风险事项至少必须具备：

> 预警信号 + 风险负责人 + 预防动作 + 回退方案。

## 8. 原文证据点：保证所有结论可追溯

### 8.1 核心目的

回答：

> 所有关键判断、决策、方法和任务，能否回到会议原文核验？

### 8.2 标准证据矩阵

| 时间戳/页码 | 发言人 | 证据摘要 | 支撑结论 | 证据类型 | 证据强度 |
|---|---|---|---|---|---|

### 8.3 证据类型枚举

| 枚举值 | 定义 |
|---|---|
| direct | 原文直接明确表达 |
| combined | 多段原文共同支撑 |
| indirect | 原文未直接表达，但上下文明显指向 |
| inferred | 基于上下文作出的合理推断 |
| pending | 无法完全确认，需要参会人核实 |

### 8.4 证据强度枚举

- strong：强
- medium：中
- weak：弱

### 8.5 核心纪律

- 不长篇复制原文；
- 不脱离上下文断章取义；
- 不把推断写成原文事实；
- 人名、数字、日期不确定时必须标注；
- 所有核心判断必须有证据；
- 所有正式任务必须有原文锚点；
- 无法确认的内容统一进入“待确认事项”。

## 9. 决策地图：区分已决、倾向、否决和未决

### 9.1 核心目的

防止会后出现：

- “我以为已经定了”；
- “我以为还没定”；
- “我理解的方向不一样”。

### 9.2 标准字段

| 决策类型 | 说明 |
|---|---|
| 已明确决策 | 已正式拍板并生效 |
| 倾向性判断 | 方向明确，但尚待补充条件或最终确认 |
| 被否定方案 | 已明确不采用 |
| 暂缓事项 | 目前不做，未来可能重启 |
| 未决问题 | 尚需补数据、补方案或继续讨论 |
| 决策依据 | 为什么作出该判断 |
| 反转条件 | 什么变化出现时需要重新决策 |
| 决策人 | 谁拥有最终决定权 |
| 生效时间 | 决策从何时开始执行 |

### 9.3 验收标准

每一项关键议题必须明确属于以下哪一类：

> 已决 / 倾向 / 否决 / 暂缓 / 未决

不得使用模糊措辞掩盖决策状态。

## 10. 分歧与争议地图：保留高价值认知冲突

### 10.1 核心目的

会议中的分歧不是噪音，而是重要的认知资产。

### 10.2 标准字段

| 分歧点 | A方观点 | B方观点 | 双方依据 | 本质冲突 | 当前处理 | 待验证事项 |
|---|---|---|---|---|---|---|

### 10.3 分歧分类

- 事实分歧；
- 数据口径分歧；
- 目标分歧；
- 优先级分歧；
- 方法分歧；
- 资源分歧；
- 风险偏好分歧；
- 价值取舍分歧。

### 10.4 验收标准

不得为了让纪要“看起来统一”而删除重要分歧。
必须写清：

- 谁持什么观点；
- 各自依据是什么；
- 本质矛盾在哪里；
- 最终如何处理；
- 后续用什么事实验证。

## 11. 业务流程与AI化流程：把会议输出转成可开发流程

### 11.1 核心目的

让会议结论能够继续转成：

- 业务流程；
- SOP；
- PRD；
- 产品Spec；
- 技术Spec；
- Agent工作流。

### 11.2 建议形成三套流程

#### 旧流程

> 原来是谁做 → 怎么做 → 经过哪些人 → 使用什么工具 → 产出什么 → 在哪里卡住

#### 新流程

> 目标 → 输入 → AI/系统处理 → 人工判断 → 输出 → 验收 → 反馈

#### 人机分工流程

| 环节 | 人负责 | AI负责 | 系统负责 | 人工确认点 |
|---|---|---|---|---|

### 11.3 四条流

- 业务流；
- 信息流；
- 数据流；
- 决策流。

### 11.4 验收标准

流程必须说明：

- 输入是什么；
- 谁作判断；
- AI处理什么；
- 系统流转什么；
- 输出是什么；
- 异常如何处理；
- 在哪里进行人工确认；
- 最终如何验收。

## 12. 指标与验收体系：让会议要求可以被验证

### 12.1 核心目的

### 12.2 四类指标

| 类型 | 作用 | 示例 |
|---|---|---|
| 过程指标 | 是否完成规定动作 | 完成20份岗位SOP |
| 结果指标 | 是否产生业务结果 | 内容生产周期缩短50% |
| 质量指标 | 输出是否稳定达标 | 专家验收通过率达到90% |
| 复利指标 | 是否沉淀可复用能力 | 形成5个跨团队可复用Agent |

### 12.3 每项指标必须包含

- 指标名称；
- 当前基线；
- 目标值；
- 统计口径；
- 数据来源；
- 统计频次；
- 责任人；
- 复盘时间；
- 未达标处理方式。

### 12.4 验收标准

没有基线、目标值和数据来源的指标，不得写入正式验收体系。

## 13. AI可读资产：把会议经验转成机器可调用能力

### 13.1 核心目的

# 六、会议分级与蒸馏深度

不是所有会议都需要蒸馏到L5。

| 等级 | 会议类型 | 建议深度 | 标准产出 |
|---|---|---|---|
| C级 | 普通沟通、日常同步、临时协调 | L1 | 会议信息、结论、任务、证据 |
| B级 | 项目推进、业务复盘、跨部门协调 | L1-L2 | 完整8维、决策、风险、任务、少量方法卡 |
| A级 | 战略会、经营会、专家会、重大复盘 | L2-L4 | 8+6维、方法卡、规则、SOP、Prompt、Eval |
| S级 | 核心方法论、AI原生组织、企业大脑、数字员工建设 | L0-L5 | 完整知识资产包与Agent闭环 |

## 6.1 分级原则

会议等级由以下因素决定：

- 对公司经营结果的影响；
- 决策金额和资源规模；
- 是否涉及组织与战略变化；
- 是否包含稀缺专家经验；
- 是否具有跨场景复用价值；
- 是否值得转成系统或数字员工。

# 十、证据、置信度与事实纪律

## 10.1 内容状态枚举

| 状态 | 含义 |
|---|---|
| fact | 原文或资料明确存在的事实 |
| decision | 会议已明确作出的决策 |
| opinion | 某位参会者的观点 |
| inference | 基于上下文作出的推断 |
| pending | 尚待确认的信息 |
| rejected | 已被会议否定的观点或方案 |

## 10.2 置信度枚举

| 等级 | 含义 |
|---|---|
| high | 有直接原文、数据或多段证据支持 |
| medium | 有较强上下文支持，但非直接表达 |
| low | 主要依靠推断，需要确认 |
| unknown | 资料不足，无法判断 |

## 10.3 AI必须遵守的事实纪律

- 不得猜测人名、日期、数字和责任人；
- 不确定时写“待确认”，不得编造；
- 推断必须明确标记为“推断”；
- 不得把个别发言人的观点写成会议决策；
- 不得把会议倾向写成已正式拍板；
- 不得删除重要分歧以制造虚假共识；
- 不得长篇复制原文；
- 不得在无证据的情况下补充“听起来合理”的内容。

# 十三、AI执行规范

本部分用于各高管直接将本文件与会议资料交给自己的AI。
AI必须严格按照以下输入、处理和输出契约执行。

---

## 13.1 输入契约

建议向AI提供以下资料：

```yaml
meeting_input:
  meeting_title: 可选
  meeting_date: 可选
  meeting_type: 可选
  participants: 可选
  raw_transcript: 必选，或提供录音转写/PDF
  slides: 可选
  spreadsheets: 可选
  chat_records: 可选
  previous_meeting_minutes: 可选
  business_background: 可选
  expected_depth: C/B/A/S，默认B
  output_language: zh-CN
```

当资料不完整时，AI应：

1. 先基于已有材料完成最大程度蒸馏；
2. 对缺失信息标注“待确认”；
3. 不得虚构；
4. 不得因为个别信息缺失而停止全部工作。

---

## 13.2 AI处理原则

AI必须按以下顺序处理：

1. 识别原始资料、会议时间与角色；
2. 还原会议背景和真实议题；
3. 区分事实、观点、决策、推断和待确认；
4. 提炼一句话判断和核心矛盾；
5. 输出从A到B的会议精神；
6. 提取已决、倾向、否决、暂缓和未决事项；
7. 保留分歧和争议；
8. 晶化方法论、判断规则和思路链；
9. 提取任务并补齐DRI、时间、交付物和验收标准；
10. 标记缺失字段，不得代替会议作决定；
11. 提取风险、预警信号和回退方案；
12. 建立原文证据矩阵；
13. 判断哪些内容值得转成L2-L5资产；
14. 输出下次复盘入口；
15. 最后执行质量自检。

---

## 13.3 AI输出顺序

AI必须严格按以下章节顺序输出：


# 十六、高管层使用方式

## 16.1 会前

会议发起人至少明确：

- 会议目的；
- 要解决的核心问题；
- 需要作出的决策；
- 预期交付物；
- 决策人和DRI。

## 16.2 会中

主持人重点控制：

- 是否围绕主要矛盾；
- 事实、判断和观点是否混在一起；
- 重要分歧是否被充分暴露；
- 是否形成明确决策；
- 是否明确责任、时间和验收；
- 是否留下可追溯证据。

## 16.3 会后

会议蒸馏负责人应：

1. 24小时内形成L1纪要；
2. A级和S级会议形成完整8+6维蒸馏；
3. 将任务同步到正式行动台账；
4. 将高价值方法送入知识蒸馏流程；
5. 在下次会议前更新任务和验证结果；
6. 复盘后修订知识资产版本。

# 十七、V4.0最终总公式

> **会议原文 → 事实还原 → 矛盾判断 → 状态转移 → 决策提纯 → 分歧保留 → 方法晶化 → 任务闭环 → 风险控制 → 证据追溯 → AI资产化 → 业务执行 → 反馈复盘 → 组织进化**

V4.0最终解决的不是“会议纪要写得够不够完整”，而是四个更高层的问题：

1. 这场会议形成了什么关键判断？
2. 这场会议推动了什么具体行动？
3. 这场会议沉淀了什么可复用能力？
4. 这些能力能否进入知识库、数字员工和业务系统持续产生结果？

因此，本系统的最终定位是：

> **以会议为入口，以判断为核心，以决策为方向，以任务为闭环，以知识资产为沉淀，以AI和数字员工为放大器的组织能力生产系统。**
