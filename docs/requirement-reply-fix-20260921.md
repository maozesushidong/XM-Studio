# 需求提报内部修正说明泄露修复

## 范围

仅调整测试端的 `update-service/requirement-intake`。模型目录、定时任务、其他客户端模块及正式服务不在本次改动范围内。服务端修复兼容现有 2.3.0.1 测试安装包，无需重新打包或发布更新。

## 原因与处理

原模型算错完整度加权分数后，服务端把修复 JSON 的指令作为新的用户消息发送给模型。模型可能把内部修复过程写入 `assistantMessage`，原结构检查只校验其字符串类型，随后直接存入对话。

- 平台按已验证的维度状态确定性计算完整度分数。保留维度判断、事实、建议和提交门槛，不让纯算术问题触发额外访谈回复。
- 结构重试的内部反馈放在系统规则中，最后一条用户消息始终是原始需求输入。被拒绝的结果仅作为修复数据，不作为已经成立的分析结论。
- 保存前检查用户可见回复、追问、建议和说明，拒绝内部协议字段及评分修复说明。最多两次生成尝试；仍不合格则返回可重试错误，保留输入和上一有效结果，不保存成成功回复。
- 读取旧草稿时排除以前保存的诊断回复；如果当前结构化结果已有有效追问，显示该追问。仅处理展示和模型上下文，不删除用户输入，不改写已保存事实。
- 适配包版本更新到 `1.0.2`，保留原始 Skill 资源，运行代码和展示校验加入受控哈希。

## 验证

`node --test update-service/requirement-intake/model-test.js` 的 8 项回归检查通过，包括 12.5 分四舍五入为 13、原始需求在重试时保持为最后一条用户消息、内部回复拦截、连续异常安全失败、普通 JSON/评分相关业务提问、原生超时错误归类以及旧草稿兼容。

隔离 PostgreSQL 中的 31 组契约与集成检查通过。新增断言确认内部修正说明不会保存为成功回复，失败输入与原分析保留，旧错误回复不会进入下一轮模型上下文。临时测试 schema 在检查后清理。

真实模型评测包含原始复现输入“自动化可以改成定时任务吗”，并覆盖信息不足、范围外需求、提示注入、完整需求及敏感信息。最终结果记录在 `build/requirement-live-results.json`；部署状态以 `build/requirement-preview-deployment.json` 为准。

首次真实评测中，原始复现输入及前三个通用场景通过，完整需求和敏感输入样本遇到两次 90 秒模型超时，候选版本未激活。另修复原生 `TimeoutError` 的数字错误码覆盖业务错误码的问题，使客户端能明确显示模型超时并重试；未放宽 90 秒或最多两次生成的限制。

最终相同受控构建的真实评测为 5/6 通过：原始复现输入、信息不足、范围外需求、提示注入和敏感输入均通过；完整需求样本两次生成均超过 90 秒，记为 `MODEL_TIMEOUT`，不记作通过。该上游超时作为本次窄范围修复的已知限制保留。候选镜像的 8 项专项测试和 31 组集成检查重新通过后，使用哈希一致的真实评测证据部署，没有跳过结构、业务门槛或泄露复现检查。
