### 需求提报响应耗时诊断

同一测试服务、同一个 `gpt-5.6-luna` 的直接最小文本请求耗时 3,083 ms，小型 JSON 请求耗时 3,398 ms；普通 DeepSeek/Gemini 健康请求约 1-3 秒。需求提报历史成功请求耗时约 46-113 秒，真实评测还出现过两次 90 秒生成均超时。

主要瓶颈是需求提报分析负载而非客户端渲染或数据库：每轮当前携带约 23,030 个字符的受控 Skill 方法、完整输出 Schema、能力元数据和对话状态，并要求生成较大的结构化结果；结构或业务校验失败时最多再生成一次。本次不缩减受控规则、输出字段或校验门槛，性能优化应单独验证，避免为了提速破坏分析质量与契约。

### 定时任务

导航改为“定时任务”。列表支持全部、运行中、已暂停、已错过；创建和编辑使用弹窗；单次、每天、每周均有对应时间设置，旧间隔任务仍可编辑。

支持任务名称、指令、工作目录、模型、技能、日期区间，启用或暂停计划、立即运行、运行中暂停、继续执行、删除和每项任务的运行记录。执行记录保存在当前用户本机，展示真实结果、失败原因、时间和附件入口。

手动运行不会移动或消耗未来的原定计划。单次任务在计划触发后结束；提前手动运行仍保留原定时间。退出、休眠或离线错过的计划标记“已错过”，不会启动后自动补跑；可以手动补跑。重启时将未完成执行记录标为中断，不伪造成功。

### 需求提报

对话区展示追问、阶段理解与最终摘要；右侧为需求理解、能力关系、事实、待确认项与建议方案；“我的提报”采用左列表、右只读详情，保留搜索与分页。

受控 Skill 在测试服务内部运行，无需员工安装。原包哈希校验保留，专用适配版本更新为 1.0.1，运行上下文实际加载上游 Skill 的追问、推理与分支方法，以及 questioning-engine 和质量门禁的适用部分。通用渠道的自动建号、通知及个人路径不进入执行链路。

原先用户的两次分析失败均为 `CAPABILITY_VERSION`：模型在资料不可用时清空了仍存在的能力版本。本次把这些平台元数据作为精确输出约束，并给结构修复提供具体原因；没有降低业务信息或摘要校验门槛。

输入先保存，分析失败保留上一有效状态；支持重试、暂存、恢复、修正、能力复评。摘要确认与提交是两个独立操作；坚持提交在独立弹窗填写理由，不改写 AI 原建议。正式提交原子生成唯一 REQ ID，重复请求不重复建号；后台单条导出沿用相同 ID。
